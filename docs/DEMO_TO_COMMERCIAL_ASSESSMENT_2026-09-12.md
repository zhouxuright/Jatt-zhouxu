### 1.4 本次修复的 5 个真实缺陷

这些都是"用户点了按钮会失败"级别的问题，此前文档未记录：

| # | 缺陷 | 症状 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **上传格式校验过严** | `.md` 传 `text/plain`、`.docx`/`.txt`/`.doc` 传 `application/octet-stream`、空 content-type 全部 **400 拒绝** | 真实浏览器对纯文本类文件上报 MIME 极不一致，而代码把"未知 MIME"当作非法 | 改为**扩展名主判据** + 通用 MIME 放行 + magic bytes 兜底（`core/validators.py`） |
| 2 | **TTS 返回 0 字节** | 接口 200 但音频长度为 0，前端播放无声 | 前端传 `voice="female_formal"`（预设 ID），被直接当作 edge-tts 语音名传入 → 抛异常被静默吞掉 | 新增 `resolve_voice()`：预设 ID → 真实语音名，非法值回退默认（`services/tts_service.py`） |
| 3 | **联网搜索恒返回空** | 200 但 `total_found: 0`、`error: null`，前端展示空白且无提示 | `docker-compose` 未注入 `SEARCH_ENGINE`/`SERPER_API_KEY`，容器内三个搜索 Key 全空 → 落到百度抓取路径 | 注入环境变量 + 引擎缺 Key 时自动回退 + 三次重试 + 失败时给出可诊断的错误信息 |
| 4 | **深度思考接口 500** | `/reasoning/deep-think` 返回 500 | `irac_analysis: dict[str, str]`，但 LLM 返回的 `confidence` 是 float → Pydantic 校验失败 | 改为 `dict[str, Any]`（`api/v1/deep_think.py`、`agents/deep_thinking_agent.py`） |
| 5 | **PDF 恶意模式误杀** | 正常合同 PDF 被拒 | 裸 `MZ` 字节规则扫描 PDF 前 4KB，压缩流中随机出现概率约 6% | 移除无意义的 `MZ` 规则，改为检测真正的 PDF 主动内容（`/JavaScript`、`/OpenAction`、`/Launch`） |

修复后复测：**上传格式矩阵 9/9 通过，全功能冒烟 14/14 通过。**

## 二、2026 年商业化 AI 法律产品是怎么做的（联网调研结论）

### 2.1 全球格局：从"AI 助手"到"AI 代理团队"

2026 年的分水岭是 **Agentic（代理式）** 取代 Assistant（助手式）。行业标杆：

| 产品 | 2026 动态 | 值得抄的做法 |
|---|---|---|
| **Harvey AI** | 估值 80 亿美元，成为美网首个官方法律助理 | 研究 + 起草 + 自动化一体化，端到端承接整个法律工作流 |
| **Thomson Reuters CoCounsel** | 用户破 100 万，2026 年初上线代理式工作流 | 深度研究跨 Westlaw + Practical Law 多源；律师可**保存/共享自定义工作流**给代理自动执行 |
| **LexisNexis Protégé General AI** | 四代理协同 | **编排代理 + 法律研究代理 + 网络搜索代理 + 客户文档代理** —— 与本项目架构思路一致 |
| **Ironclad Assistant** | 统一续约、成本识别、收件、红线修改代理 | 把日常合同工作做成端到端系统，而非散点工具 |
| **Crosby（AI 律所）** | AI 累计审阅 1.3 万份合同，营收增长约 400% | **"AI 预处理 + 持证律师终审"**商业模式，AI 承担 80% 基础工作 |

### 2.2 中国市场格局

| 产品 | 形态 | 关键点 |
|---|---|---|
| 律通人合「典典 AI 律助 OS」 | 全链条生态 | 技术基座 **LegalHarness** 采用"思考—行动—观察"自适应回路；覆盖民事/刑事/行政三大诉讼领域 + 十余项功能，含**量刑区间预测、合同风险分级标注** |
| 法义经纬「律界芯盒 / 钳箱」 | **软硬一体本地化部署** | 直击"数据安全"这一行业第一痛点，法律 AI 装进律所内网，**数据不出域** |
| 法大夫「企业法律顾问智能体」 | 企业法务全生命周期 | 九大核心模块打通法务全流程，**支持小程序/PC/Pad 多端协同**，从被动应对转为主动预警 |
| 德恒「Lawyerdocs」 | 自研 | Dify 工作流 + Ollama 本地模型，文档处理到文书生成全链条自动化 |

### 2.3 一个商业化产品必须具备的六大能力域

行业共识是：**从"能回答问题"升级到"能办成事"**。

1. **合同全生命周期**：起草 → 审查 → 版本比对 → 红线修改 → 归档（闭环，不是单次问答）
2. **诉讼支持**：证据清单、庭审提纲、类案比对、**裁判预测**（输出可入卷的可读文书）
3. **合规风险管理**：法规动态每日跟踪、企业风险自动排查、违规项分级
4. **多智能体协同**：检索/起草/审查/合规 Agent 像律师团队一样分工，由编排层调度
5. **数据安全与私有化部署**：数据不出内网 + 权限体系 + 审计日志 + 等保合规 —— **商业化的前提**
6. **个性化定制**：融入企业自有知识库、合同模板、业务流程，才能支撑客单价

> 对照本项目：这六项**都有雏形**（`lifecycle` / `litigation` / `compliance` / `collaboration` / `enterprise` 路由 + 三层上下文 + MCP + skills），但**深度不足，属"有框架、缺血肉"**。

### 2.4 必须知道的风险：幻觉就是产品死亡线

2026 年行业最硬的教训：

- **斯坦福研究实测错误率**：Lexis+ AI 辅助检索 **17%** 错误，Westlaw AI 辅助检索 **34%** 错误
- 全球 **700+ 起** 法院案件涉及 AI 虚构引注，处罚从警告到五位数罚款
- 中国司法部数据：2025 年底执业律师已突破 **83 万人**；行业已出现"AI 引用废止法条、编造案例"引发的信任危机
- "AI 让我这么写的"在 2026 年已被视为**执业过失**，人在环（HITL）成为伦理强制要求

**对本项目的直接含义**：`court_cases` 表里 121 万条开源案例的**商用许可必须逐源核验**；而那 1,500 万条模板合成的假案号（如"（2018）市鼓民初第 76972 号"）**一旦展示给用户，就是主动制造虚假引用**。前一位工程师决定不入库是**正确**的，本次评估保留该决定并将边界制度化。

若面向境内公众提供生成式 AI 服务，需同时完成：

## 四、数据扩充：如何正确走向上亿（诚实版）

### 4.1 本次实测的关键发现

我核对了本地所有数据资产，得出一个必须正视的结论：

| 检查项 | 结果 |
|---|---|
| 法规全文数据（`laws.json.zip`，102 MB） | 22,552 部，125.7 M 字符全文 |
| 该数据集去重后的 (法规, 法条号) 组合 | **665,077 条** |
| 现有 `legal_articles` 表 | **686,906 条**（已超出本地可得量） |
| 结论 | ✅ **法规全文已 100% 入库，没有缺口** |
| `laws_qa_pairs.jsonl` | 873,678 行 = 表内 873,678 条 ✅ 已全量入库 |
| `law_knowledge_entries.jsonl` | 194,339 行 = 表内 194,339 条 ✅ 已全量入库 |
| `law_cross_references.jsonl` | 20,219 行 = 表内 20,219 条 ✅ 已全量入库 |

**也就是说：本地所有真实公开法律数据，已经全部导入完毕。免费公开数据源已被用尽。**

### 4.2 为什么"上亿"不能靠爬虫和开源数据实现

| 数据源 | 量级 | 性质 | 商用可行性 |
|---|---|---|---|
| 中国裁判文书网 | 1.6 亿+（1985–2025） | 真实判决 | ⚠️ 需授权；大规模爬取有反爬与权属风险，商业化产品不应作为主力 |
| 威科先行 / 北大法宝 / 无讼判例 / 把手案例 | 数千万–1.5 亿 | 权威法规 + 判例 + 期刊 | 💰 **必须商业采购**，年费约 10–50 万+ |
| 国家法律法规数据库（flk.npc.gov.cn） | 5 万+ | 权威法条 | ✅ 免费公开 —— **本项目已全部导入** |
| 开源法律数据集（CAIL、DISC-LawLLM 等） | 约 2,500 万 | 多为 SFT 训练语料 | ⚠️ 多为研究许可，非清洗后的可检索法条/判例 |
| 程序化合成 | 理论无限 | **非真实数据** | ✅ 仅可用于微调/压测，**严禁作为判例展示** |

**核心结论：上亿条"真实、可溯源、可商用"的法律数据 = 必须采购商业数据库授权。没有第二条路。**

### 4.3 推荐的三步走路径

**第一步（0 成本，已完成）— 免费权威数据打底**
- 国家法律法规数据库全量：已导入 18,580 部法规 / 686,906 条法条
- 开源判例与问答：已导入 121 万案例 + 87 万问答
- 产出：**2,619,148 条可引用语料**

**第二步（约 10–50 万/年，6–8 周）— 采购商业授权补齐核心**
- 采购"裁判文书 + 法规 + 期刊"商业授权（威科先行 / 北大法宝 / 无讼 等）
- 关键是**拿到书面商用授权**，而非数据本身
- 预期：可引用语料升至 **3,000 万–1 亿条**

**第三步（自有资产）— 合成数据只用于训练，不入检索库**
- 现有 1,500 万条合成数据（16 GB）用于：模型微调（SFT）、检索压测、评测集
- **已在 `corpus_registry` 中标记为 `synthetic` + `citable=false`，边界制度化**

### 4.4 本次交付的数据治理基础设施

新增两个生产级工具（已进镜像）：

| 文件 | 作用 |
|---|---|
| `backend/scripts/corpus_audit.py` | 语料治理审计：实测各源条数，写入 `corpus_registry` 表，按"可引用/不可引用/合成"分层 |
| `backend/scripts/import_law_fulltext.py` | 权威法规全文导入器（幂等、分批、可 limit/断点），为采购数据接入做好通道 |
| `GET /api/v1/admin/corpus-registry` | 新增管理接口，把数据家底做成可审计台账 |

> 这解决了一个商业化必需的能力：**任何一条数据，都能回答"它从哪来、能不能商用、能不能给用户看"。**

## 六、多轮对话上下文窗口方案（当前实现）

用户关心的"对话要一直持续下去"，现有实现是**三层上下文管理器**（`services/context_manager.py`，42 KB），实测有效：

```
第 1 层：滑动窗口     → 保留最近 N 轮原文，保证近期语境精确
第 2 层：增量摘要压缩 → 早期对话压缩成摘要（实测 summary_length=281）
第 3 层：事实表       → 结构化抽取当事人/争议焦点/已确认事实/待解问题/时间线
                        实测：2 位当事人、3 个争议焦点、3 条已确认事实、2 个时间线事件
```

实测验证：连续 3 轮对话（入职信息 → 追问试用期 → 追问赔偿），第 3 轮仍正确引用第 1 轮的"上海/3 年合同/6 个月试用期"事实 → **PASS**。上下文预算 33,000 tokens。

**建议增强（P1）**：跨会话长期记忆（把 `fact_sheet` 持久化到企业客户档案），以及基于语义的窗口裁剪替代纯长度裁剪。

## 十、结论

这个项目**已经不是 demo 的水平**：功能端到端全部跑通（14/14），架构（多智能体 + RAG + 向量库 + 知识图谱 + MCP + Skills）与行业头部产品思路一致，多轮上下文与语音对话都已真实可用。本次还修掉了 5 个会导致用户操作失败的真实缺陷。

**但它还不是一个可收费的产品**，卡点非常明确：

> **功能已齐，数据授权未到，合规资质未办，生产深度不足，商业闭环未建。**

其中**最紧急的不是写代码，是启动大模型备案**——那是 6–8 个月的行政周期，且决定这个产品能不能合法上线。其次是**数据授权采购**——那是走向上亿条可引用语料的唯一通路，没有任何技术手段可以绕过。

技术上最该做的下一步，是把"引用可溯源"做成闭环：让每一句法律结论都能点开原文。这既是抑制幻觉的手段，也是法律 AI 唯一能建立信任的方式。
